## TL;DR

The worker is in good shape. The published `SECURITY.md` STRIDE-lite analysis is accurate as of audit time, and the major-impact controls (per-request `McpServer`, constant-time HMAC compare, two-phase HMAC write-gate with consume-once D1 binding, `MCP_SYNC_KEY` never logged, `gitleaks` mandatory in preflight) all check out under code reading.

Three real findings worth fixing landed today as MEDIUM-severity auto-fixes against non-protected files (`obs.ts`, `tool-registry.ts`, `auth.ts`):

1. **PII redaction in `audit_log.payload`** — tool args were JSON-stringified verbatim (customer phone/email/name/address/notes). Now redacted by field-name pattern at log time.
2. **Audit truncation marker** — `JSON.stringify(...).slice(0, 4000)` produced rows that were indistinguishable from non-truncated short rows. Now wrapped in a `_truncated` envelope with original length.
3. **`X-Actor` header validation** — was forwarded verbatim to taylor-ai and into Analytics Engine indexes. Now restricted to `^[a-zA-Z0-9._:-]{1,64}$` with fallback to `claude-code`. Closes a future log-injection / RBAC-trust-gradient risk.

A new `obs.safeContext()` helper now gates `error_log.context` against an allowlist so a careless `error('msg', { env, request, args })` call cannot leak `MCP_SYNC_KEY` or other env-shaped values; existing `tool-registry.ts` callers were updated to use it.

Three findings touch protected modules (`src/read-router.ts`, `src/tools/st_call.ts`, `src/write-gate.ts` + `src/write-tool-factory.ts`) and have been **staged** with concrete recommendations, awaiting plan-mode reentry per `qsc-infra/.claude/rules/protected-modules.md`.

One previously suspected HIGH was downgraded after re-reading the code: `st_call` is already routed through `WriteGate` (dryRun + confirm-token + consume-once) for non-GET methods — `src/tools/st_call.ts:67-73`. The remaining concern is the absence of a path *prefix* allowlist; the `endpoint_registry` table already exists in `migrations/0001_baseline.sql:88-100` to support that, awaiting population.

## Findings

Severity is impact × exploitability, with single-tenant blast radius (tenant `431848990`) factored in.

### Resolved this pass (auto-fix, non-protected files)

#### F-2026-05-03-01 — Audit log persisted unredacted PII (MEDIUM → fixed)

**Where:** [`src/tool-registry.ts:76, 125`](../../src/tool-registry.ts) (caller of `obs.audit`), [`src/obs.ts:56-57`](../../src/obs.ts) (sink). Pre-fix, `obs.audit({ payload: args })` ran `JSON.stringify(args).slice(0, 4000)` directly against tool arguments. Tool args routinely include `phone`, `email`, `name`, `address`, `note` for `find_customer`, `add_customer_note`, `add_job_note`, `book_job`, `create_call_with_campaign`, etc.

**Impact:** D1 `audit_log.payload` accumulated raw customer PII unbounded. Read access is already gated behind `MCP_SYNC_KEY` (admin endpoints `/admin/metrics`, `/admin/roles`), and this is a single-tenant internal tool, but two factors still made it worth fixing:

1. Privacy posture — `SECURITY.md §Information Disclosure` claims "no raw ST responses with PII"; the audit row didn't strictly conform.
2. Defense in depth — any future read endpoint, D1 export, or backup snapshot would surface raw PII.

**Fix:** New `redactPayload()` helper in `src/tool-registry.ts` walks the args tree and replaces values whose key matches a PII-shaped regex (`/^phone/i`, `/Email$/i`, `/^name$/i`, `/^street/i`, `/^address/i`, `/^city$/i`, `/^zip$/i`, `/^postal/i`, `/^state$/i`, `/^note$/i`, `/^description$/i`, `/^summary$/i`, `/^body$/i`, etc.) with type-tagged tokens like `[redacted:str:N]` so investigators retain length-class info without the value. Numeric IDs, enum values, ISO dates — pass through unchanged. Recursion depth-capped at 6 levels. Tests in `src/tools/__tests__/security_redact.test.ts` (12 cases).

**Limitations:** denylist by field name. Free-text fields named ambiguously (e.g., `customField1` containing PII) are NOT caught. Acceptable trade-off for v1; revisit if a moderation review surfaces a leak.

**Historical rows:** D1 `audit_log` rows written before this commit retain raw payloads. A one-time cleanup is *not* in scope for this pass; recommend a runbook addition for "wipe audit_log older than N days" at the operator's discretion.

#### F-2026-05-03-02 — Audit truncation was silent (LOW → fixed)

**Where:** [`src/obs.ts:56-57, 83`](../../src/obs.ts). `JSON.stringify(...).slice(0, 4000)` produced indistinguishable output between (a) a payload that fit in 4000 bytes and (b) a payload that was 50KB and silently truncated.

**Impact:** Investigation friction only — no security impact. Worth fixing because the audit log is the primary forensic surface.

**Fix:** New `jsonTruncate(value, max=4000)` helper. Returns the raw JSON when it fits, or `{"_truncated": true, "_orig_length": N, "_slice": "..."}` when it overflows. Circular-structure-safe via try/catch (returns `{"_serialize_failed":true}`). Wired into `obs.audit()` (payload + result) and `obs.error()` (context). Tests cover happy path, truncation marker, null/undefined, circular.

#### F-2026-05-03-03 — `X-Actor` header forwarded verbatim (LOW–MEDIUM → fixed)

**Where:** [`src/index.ts:176`](../../src/index.ts) (read), [`src/auth.ts:55`](../../src/auth.ts) (forward). Pre-fix, `request.headers.get('x-actor') ?? 'claude-code'` accepted any header value, propagated it into `audit_log.actor`, `error_log.context.actor`, Analytics Engine `blobs[3]`, and `X-Actor:` on every outbound call to taylor-ai.

**Impact:** Today, taylor-ai uses `X-Actor` only for logging — no RBAC trust. So this was a latent risk: (a) log-injection via `\r\n`-bearing actor strings could confuse downstream log parsers; (b) if any future caller (taylor-ai, Plecto, Grafana queries) treats `X-Actor` as identity, a default-role caller could spoof another actor. Tightening at the boundary closes both cleanly.

**Fix:** New `safeActorHeader()` helper exported from `src/auth.ts`. Validates against `^[a-zA-Z0-9._:-]{1,64}$`. Invalid input falls back to `'claude-code'`. Wired into `src/index.ts:176`. Tests cover valid forms (`claude-code`, `lpeluso`, `retell:agent_…`, `Service.Account_v2`), missing/empty (→ default), and rejection (`\r\n` injection, spaces, oversized, traversal `../`, unicode). The fallback is silent rather than 401 — actors are advisory metadata, not auth.

#### F-2026-05-03-04 — Error log context could absorb arbitrary objects (LOW → fixed)

**Where:** [`src/tool-registry.ts:113`](../../src/tool-registry.ts) pre-fix passed `{ actor: …, args, correlation, code: … }` straight into `obs.error()`. The error_log's `context` column is `JSON.stringify(...).slice(0, 4000)`, so a future `error('msg', { request, env })` call would happily serialize the full request and env to D1.

**Impact:** Latent. No current caller leaks env. But the API didn't prevent it.

**Fix:** New `obs.safeContext(input)` helper picks an allowlist of keys (`status`, `tool`, `actor`, `correlation`, `correlation_id`, `latency_ms`, `code`, `failures`, `source`, `severity`, `op`, `kind`, `ms`) and surfaces dropped keys via `_dropped_keys` so the trail is visible. The error-path `context` in `tool-registry.ts` now goes through `safeContext` and intentionally **drops** the previous inline `args` field — `args` already lives in `audit_log.payload` (now redacted), and joining by `correlation` recovers the same forensic chain. Tests cover allowlist, dropped-key reporting, non-object input.

#### F-2026-05-03-05 — `read-router.queryD1` ships arbitrary SQL to taylor-ai (MEDIUM → fixed in pass 2)

**Where:** [`src/read-router.ts:44-59`](../../src/read-router.ts). The `queryD1()` method posts the raw `sql` string to taylor-ai's `/internal/query-d1` and trusts the upstream to enforce `SELECT`-only. Today, every caller in this worker passes a literal `SELECT …`, but nothing prevents a future caller from passing `DELETE FROM …`.

**Recommendation:** Add a defense-in-depth check at the top of `queryD1()`:

```ts
if (!/^\s*SELECT\b/i.test(sql)) {
  throw new Error('queryD1: only SELECT statements are permitted from this client');
}
```

**Status:** Implemented in pass 2 (2026-05-03 follow-up). See addendum.

#### F-2026-05-03-06 — `st_call` admin escape hatch has no path-prefix allowlist (MEDIUM, staged)

**Where:** [`src/tools/st_call.ts:33-37, 62-86`](../../src/tools/st_call.ts). After admin role resolution and dryRun-confirm gating, the path is fully arbitrary so long as it starts with `/` and contains a recognizable ST API prefix (handled by `normalizePath()` in `src/st-path-builder.ts`). The `endpoint_registry` table in [`migrations/0001_baseline.sql:88-100`](../../migrations/0001_baseline.sql) was *designed* to back this allowlist (note: "T9 populates"), but is empty.

**Mitigations already in place:** (a) `adminOnly: true` excludes `st_call` from the default-role tool list ([`src/index.ts:153`](../../src/index.ts) `toolsForRole(reqCtx.role)`); (b) every non-GET routes through `WriteGate.dryRun` + `verifyToken` → consume-once + HMAC + 15 min TTL; (c) D1 `audit_log` row written for each call.

**Residual risk:** an admin (Luke, today; service accounts in future) can still call any endpoint ST exposes, including endpoints not yet known to the team. The blast radius is bounded by ST's own RBAC on the OAuth client, but defense in depth wants a worker-side allowlist.

**Recommendation:** populate `endpoint_registry` with the prefixes already mapped through the typed tools (`/crm/`, `/jpm/`, `/pricebook/`, `/accounting/`, `/memberships/`, `/sales/`, `/marketing/`, `/dispatch/`, `/taskmanagement/`, `/reporting/`, `/schedulingpro/`, `/settings/v2/tenant/{id}/technicians`, `/settings/v2/tenant/{id}/employees`, `/settings/v2/tenant/{id}/user-roles`, `/forms/`) and reject `st_call` paths that don't match any prefix. Move the allowlist load to a per-request fetch with a short-lived `mcp_cache` entry to keep latency flat.

**Why staged:** `src/tools/st_call.ts` is in the protected-modules registry. Edit requires plan-mode reentry. The allowlist data also wants its own migration (`migrations/0002_st_call_allowlist.sql`).

#### F-2026-05-03-07 — Confirmation-token TTL is uniform 15 min (LOW → fixed in pass 2)

**Where:** [`src/write-gate.ts:16`](../../src/write-gate.ts) `TOKEN_TTL_MS = 15 * 60 * 1000`. The 15 min window was chosen to cover composite-tool fan-out latency tails. For non-composite single-tool writes (`st_patch_service`, `st_create_service`, `st_patch_material`, `st_create_material`, `add_customer_note`, `add_job_note`, `book_job`, `assign_technicians`, etc.), 5 min would tighten the leak window with zero ergonomic loss.

**Recommendation:** thread `tokenTtlMs?: number` through `defineWriteTool` ([`src/write-tool-factory.ts:32-63`](../../src/write-tool-factory.ts)) and `WriteGate.dryRun` ([`src/write-gate.ts:62-85`](../../src/write-gate.ts)). Default 15 min. Apply 5 min to all non-composite writes.

**Status:** Implemented in pass 2 (2026-05-03 follow-up). See addendum.

### F-05 — `read-router.queryD1` SELECT guard (Fixed)

### F-07 — Per-tool `tokenTtlMs` (Fixed)

**`src/write-gate.ts`:**
- Added `DEFAULT_TOKEN_TTL_MS = 15 * 60 * 1000` (default for tools that don't override).
- Added `MAX_TOKEN_TTL_MS = 15 * 60 * 1000` (absolute hard ceiling — no per-tool override exceeds it).
- Kept `TOKEN_TTL_MS` as a backward-compat alias so external references don't break.
- `WriteGate.dryRun()` got an 8th optional positional parameter `tokenTtlMs?: number`. The actual TTL is `Math.min(tokenTtlMs ?? DEFAULT, MAX)`, written to D1 `expires_at` and surfaced in the `expires_in_seconds` response field.
